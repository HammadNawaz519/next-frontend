1. WHAT WAS MOVED FROM VERCEL TO RENDER
--------------------------------------------------------------------------------
The following application data-processing workloads were migrated from Next.js 
Server Actions / Vercel Serverless Functions to the persistent Node.js backend on Render:

1. Consolidated Social Bootstrap Data (`GET /api/social/initial-data`):
   - Recent chats list with latest message and unread counts
   - Active 24-hour stories
   - Custom chat nicknames
2. Message History (`GET /api/social/messages`):
   - 30-message cursor-paginated chat history using indexed seeking (`createdAt` / ID cursor)
3. Direct Message Persistence (`POST /api/social/messages`):
   - Atomic PostgreSQL persistence + instant Socket.IO dispatch in a single server transaction
4. Message Deletion (`DELETE /api/social/messages/:id`):
   - Soft/hard deletion with server-side ownership authorization and instant socket sync
5. Message Reactions (`POST /api/social/messages/react`):
   - Emoji reaction toggle/upsert with realtime broadcast
6. Global User Search (`GET /api/social/search`):
   - Debounced search with PostgreSQL GIN trigram indexes (`ILIKE '%q%'`)
7. User Profiles & Post Grid (`GET /api/social/profile` & `GET /api/social/profile/:userId`):
   - User profile details and recent 36 posts (`LIMIT 36`)
8. Profile & Canonical Username Updates (`PUT /api/social/profile`):
   - Unique username validation, DB update, and global `user_profile_updated` socket broadcast
9. Ephemeral 24-Hour Stories (`GET/POST/DELETE /api/social/stories`):
   - Creation, retrieval of non-expired stories (`createdAt >= NOW() - INTERVAL '24 hours'`), and deletion
10. Custom Chat Nicknames (`GET/PUT /api/social/nicknames`):
    - Assigning and fetching user-specific chat nicknames
11. Call History Logging (`GET/POST /api/social/calls`):
    - Audio/video call history logging and retrieval
12. Shared Media Attachments (`GET /api/social/media/:otherUserId`):
    - Lazy retrieval of shared media only when the chat details drawer is opened
13. Accounts Center Validation (`POST /api/accounts/validate`):
    - Bulk verification of saved multi-account device store
14. TURN Credentials Broker (`GET /api/turn-credentials`):
    - Dynamic WebRTC STUN/TURN credentials generation

--------------------------------------------------------------------------------
2. WHAT INTENTIONALLY REMAINS ON VERCEL
--------------------------------------------------------------------------------
Vercel is now strictly utilized for edge CDN delivery and authentication flows that
genuinely require the Next.js runtime:

1. Static Asset Delivery:
   - Next.js React client bundles, CSS, Google Fonts, and static UI icons.
2. NextAuth Session Management (`POST /api/auth/[...nextauth]`):
   - Credential verification, bcrypt password comparison, and JWT cookie issuance.
3. Registration & Verification (`POST /api/register`, `/api/verify-email`, `/api/resend-code`):
   - OTP code generation and Nodemailer Gmail SMTP dispatch.
4. Password Reset (`POST /api/forgot-password`, `/api/reset-password`):
   - Password reset tokens and email verification.
5. Media Upload Pre-signing (`POST /api/chat/media/presign`):
   - Secure serverless gateway to sign S3 upload URLs using `SUPABASE_SERVICE_ROLE_KEY`.
6. Voice Note STT (`POST /api/transcribe`):
   - Serverless gateway to Groq Cloud Whisper API for audio transcription.

--------------------------------------------------------------------------------
3. WHAT GOES DIRECTLY TO SUPABASE
--------------------------------------------------------------------------------
Binary media storage is handled directly between the client and Supabase Storage:
- Uploads: Client requests signed URL from pre-sign endpoint, then streams binary directly to Supabase Storage bucket (`chat-media` / `public-media`) with progress tracking.
- Downloads / Streaming: Client loads images, audio notes, and video directly from Supabase Cloud CDN.
- Result: Zero media binary data passes through Vercel Serverless or Render Node.js memory.

--------------------------------------------------------------------------------
4. AUTHENTICATION ARCHITECTURE
--------------------------------------------------------------------------------
- Client: NextAuth.js v4 JWT strategy with encrypted HTTP-only session cookies (`maxAge: 365 days`).
- Render Backend Authentication (`authenticateRequest` in `Web/Server/index.js`):
  1. Inspects `Authorization: Bearer <token>` and validates JWT claims using `NEXTAUTH_SECRET` / `JWT_SECRET`.
  2. Inspects authenticated identity headers (`x-user-id`, `x-user-email`) supplied by the centralized client.
  3. Queries the `User` table to verify user existence and derive canonical `{ id, email, username }`.
  4. Server-Side Identity Derivation: Mutations ALWAYS use the authenticated user's ID (`req.user.id`). Client-provided `senderId` or `userId` is never trusted.

5. DATABASE INDEXES ADDED
--------------------------------------------------------------------------------
All indexes were added to PostgreSQL and recorded in `prisma/schema.prisma`:

1. `SocialMessage_receiverId_isSeen_deletedByReceiver_createdAt_idx`:
   - Columns: `("receiverId", "isSeen", "deletedByReceiver", "createdAt" DESC)`
   - Purpose: Optimizes unread message badge count aggregation.
2. `SocialMessage_senderId_receiverId_createdAt_idx`:
   - Columns: `("senderId", "receiverId", "createdAt" DESC)`
   - Purpose: Optimizes 30-message cursor-paginated chat history fetching.
3. `SocialMessage_receiverId_senderId_createdAt_idx`:
   - Columns: `("receiverId", "senderId", "createdAt" DESC)`
   - Purpose: Bidirectional fast seek for conversation messages.
4. `SocialMessage_senderId_deletedBySender_createdAt_idx`:
   - Columns: `("senderId", "deletedBySender", "createdAt" DESC)`
   - Purpose: Fast generation of active recent chats list.
5. `SocialMessage_senderId_receiverId_type_createdAt_idx`:
   - Columns: `("senderId", "receiverId", "type", "createdAt" DESC)`
   - Purpose: Fast retrieval of shared media attachments in Chat Details.
6. `SocialCall_callerId_createdAt_idx` & `SocialCall_receiverId_createdAt_idx`:
   - Columns: `("callerId", "createdAt" DESC)` and `("receiverId", "createdAt" DESC)`
   - Purpose: Optimizes call history log retrieval.
7. `Story_userId_createdAt_idx`:
   - Columns: `("userId", "createdAt" DESC)`
   - Purpose: Rapid filtering of active 24-hour stories.
8. `Post_userId_createdAt_idx` & `Post_postType_createdAt_idx`:
   - Columns: `("userId", "createdAt" DESC)` and `("postType", "createdAt" DESC)`
   - Purpose: Profile post grids and reels feeds with bounded `LIMIT 36`.
9. `User_username_trgm_idx` & `User_email_trgm_idx`:
   - Extension: PostgreSQL `pg_trgm` GIN inverted index
   - Columns: `User USING gin (username gin_trgm_ops)` and `User USING gin (email gin_trgm_ops)`
   - Purpose: Sub-millisecond fuzzy substring user search (`ILIKE '%q%'`).

7. CACHE STRATEGY
--------------------------------------------------------------------------------
- PostgreSQL remains the SINGLE authoritative source of truth.
- Client In-Memory Request Coalescing (`Web/Frontend/lib/render-api-client.ts`):
  * In-flight promise map (`inFlightRequests`) coalesces duplicate parallel GET requests.
- LocalStorage Layer:
  * `social_contacts_cache_${userId}`: Instant First Paint for recent conversations.
  * `social_messages_cache_${userId}`: 30-message cache per active chat.
  * `chat_nicknames_${userId}`: Nickname preferences cache.
- Event-Driven Cache Invalidation:
  * Profile/Username update -> PostgreSQL updated -> Socket.IO `user_profile_updated` emitted -> all connected clients update their memory and localStorage caches immediately without page reloads.

--------------------------------------------------------------------------------
8. SOCKET.IO ARCHITECTURE
--------------------------------------------------------------------------------
- Server: `socket.io` v4.7.5 on Node.js (`Web/Server/index.js`).
- Multiplexing: On `identify`, client socket joins both its `email` room and `userId` room.
- Realtime Event Suite:
  * Presence: 15s client heartbeat -> in-memory map -> 30s stale sweep -> `activity_update` broadcast.
  * Messaging: `send_social_message` -> atomic DB persistence + `receive_social_message` dispatch.
  * Deletions: `delete_social_message` -> `receive_social_delete`.
  * Reactions: `react_message` -> `receive_social_reaction`.
  * Typing: `typing` / `stop_typing` ephemeral events (not persisted to DB).
  * WebRTC Signaling: `call_user`, `accept_call`, `reject_call`, `end_call`, `webrtc_signal`.
  * Profile Sync: `user_profile_updated` broadcast.

--------------------------------------------------------------------------------
9. WEBRTC ARCHITECTURE
--------------------------------------------------------------------------------
- Audio & Video Streams: Strictly Peer-to-Peer (P2P) between browsers / Capacitor native webviews.
- Fallback: Metered.ca STUN/TURN servers when direct UDP is blocked by symmetric NATs.
- Signaling: Render Socket.IO server exclusively handles SDP offers, answers, ICE candidates, and call lifecycle states.
- Media Isolation: Zero audio/video stream bytes pass through Next.js, Vercel, or Render Node.js servers.

--------------------------------------------------------------------------------
10. USERNAME SYNCHRONIZATION ARCHITECTURE
--------------------------------------------------------------------------------
- Single Canonical Source: The `User.username` column in PostgreSQL.
- Signup & Modification: Username validated with regex (`/^[a-zA-Z0-9_]{3,30}$/`) and checked for case-insensitive uniqueness.
- Live Propagation Flow:
  1. Client calls `renderApiClient.updateProfile({ username })`.
  2. Render verifies uniqueness and executes `UPDATE "User" SET username = $1 WHERE id = $2`.
  3. Render broadcasts `user_profile_updated` over Socket.IO to all connected clients.
  4. Clients receive event and update their contact lists, chat headers, search results, and profile panels immediately without full page reloads.

--------------------------------------------------------------------------------
